# VersePC2 更新发布流程

本文档记录从「改代码」到「用户能自动更新到新版本」的完整发布步骤（三平台统一发布，以 1.1.2 为示例）。发布者需具备 GitHub（`doujie081231/VersePc2`）与 Gitee（`doujie081231/verse-pc2`）的写权限 Token。

---

## 一、前置：本次发布的代码改动

发布前先确认涉及哪些代码，需要重编所有还是部分平台。

需重编（改后端/前端/版本号，必须重编）：
- `src-tauri/src/*.rs`（如 `updater.rs` 下载/更新逻辑）
- `frontend/js/**`（平台显示、自更新入口等，需先跑 `prepare-frontend` 同步）
- `src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`、`src-tauri/Info.plist`（版本号）
- `src-tauri/Cargo.lock`

仅线上可改（无需重编）：
- `update.json`（下载地址/哈希，但哈希来自新包，一般落后于重编）
- GitHub/Gitee release 的草稿状态、tag、资源

> ⚠️ 版本号三处一致：`Cargo.toml` 的 `version`、`tauri.conf.json` 的 `version`、`Info.plist` 的 `CFBundleShortVersionString` / `CFBundleVersion`。

---

## 二、改代码 + 本地重编 Windows

1. 修改代码，并在关键逻辑上保持注释不带「参考 PCL」等字样。
2. 同步前端到构建目录（Tauri 的 beforeBuildCommand 会调用，也可手动确认）：
   ```bash
   node scripts/prepare-frontend.mjs
   ```
3. 本地编译 Windows（MSVC 工具链在 F 盘，需按项目环境变量加载）：
   ```
   ${MSVC}/bin/Hostx64/x64 ; ${MSVC}/include ; ${WindowsKits}/10.x.x/Include ; ${WindowsKits}/10.x.x/Lib
   cargo build --release --bin verse-tauri
   ```
4. 落盘并计算哈希(Windows 资产统一用固定名 `VersePC2.exe`,不带版本后缀):
   ```powershell
   Copy-Item src-tauri\target\release\verse-tauri.exe "dist\VersePC2.exe" -Force
   Get-FileHash -Algorithm SHA256 "dist\VersePC2.exe"
   ```
   Windows 包只本地编;macOS/Linux 交给 GitHub Actions(见第四节)。

> ⚠️ 本地 Windows 编译只验证 `cfg(target_os = "windows")` 分支。`macos`/`linux` 的 cfg 分支只有 CI 能验证，发布前务必走 CI 全量跑一遍。

---

## 三、推送代码到 GitHub main

用 **GitHub Contents API** 逐个同步改动文件到 `main` 分支（覆盖 `sha` 以更新现有文件）：

```powershell
$h = @{ Authorization = "Bearer $token"; "User-Agent" = "VersePC" }
# 对每个文件：
$content = [Convert]::ToBase64String([IO.File]::ReadAllBytes($localPath))
$g = Get "${api}/contents/${path}"          # 取当前 sha
Put "${api}/contents/${path}" {
  message, content, sha=$g.sha, branch="main"
}
```

> ⚠️ update.json 也走这里推送；它是旧客户端通过 `raw.githubusercontent.com`（及 ghfast 等镜像）读取的，推送后旧版本用户即可感知新版本。

---

## 四、GitHub：建 tag/release、上传 Windows、触发 mac/linux CI

1. **建 tag**（指向 main 最新 commit）：
   ```
   POST /git/refs   { "ref":"refs/tags/v<ver>", "sha": <main head> }
   ```
2. **建 release**（非草稿、非 pre-release）：
   ```
   POST /releases  { tag_name, name, body, draft=false, prerelease=false }
   ```
3. **上传 Windows exe** 到该 release（Upload API，`application/octet-stream`，超时给足），资产名固定为 `VersePC2.exe`（不带版本后缀）：
   ```
   POST https://uploads.github.com/repos/{o}/{r}/releases/{id}/assets?name=VersePC2.exe
   ```
4. **触发 CI 编 mac/linux**（workflow 文件已在 main，`on: workflow_dispatch`）：
   ```
   POST /actions/workflows/{workflow_id}/dispatches  { ref:"v<ver>" }
   ```
   CI 三个 job：`linux_x86_64`、`macos_arm64`（macos-14 原生 aarch64）、`macos_x86_64`（macos-14 上 `--target x86_64-apple-darwin` 交叉编译），产物直接用 `tauri-apps/tauri-action` 上传到该 release。
5. **监控** Actions run 至 completed（轮询 `/actions/runs/{id}` 与 `/jobs`）。

### 遇到 CI 失败的处理
- 修改代码后，`push 到 main` → **force-update（PATCH）tag 到新 commit**，→ 重新 dispatch。**不要 delete+recreate tag**，否则会把 release 变草稿/`untagged`（这正是之前线上 404 的根因）。
- ⚠️ 本地 Windows 编译成功 ≠ macos/linux 也成功（cfg 分支不同）。曾因 macOS 分支里 `app` 变量遮蔽了 `AppHandle` 参数导致 `app.exit(0)` 编译失败，需重推重跑。

## 五、下载 mac/linux 产物并算哈希

1. 从 release 的 GitHub 拿**平台对应包的 SHA-256**。更快的办法：直接读 release asset 对象的 `digest` 字段（GitHub 已按实际字节算好），无需全量下载：
   ```powershell
   GET /releases/tags/v<ver>   # 每个 asset 带 .digest = "sha256:..."
   ```
2. 若要包本体：用镜像下载更快且稳（直连 GitHub 会被墙）：
   ```
   curl -L -C - -o <name> "https://ghfast.top/https://github.com/{o}/{r}/releases/download/v<ver>/<name>"
   ```
   **下载后务必校验 size 与 hash 全等**，避免网络截断导致损坏。
3. 四个包的哈希/大小写入 update.json。

### 若本地哈希与 digest 不一致
以重新构建出的产物为准，重新跑 CI 覆盖，绝不要把不一致的哈希写进 update.json。

---

## 六、Gitee：建 release、上传四包

Gitee release 的下载速度快、也是 update.json 里四平台的**首选下载源**（`build_download_sources` 会优先打 Gitee）：

1. 创建 tag + release（`POST /api/v5/repos/{o}/{r}/releases`，`tag_name=v<ver>`，`target_commitish=master`，非 pre-release）。
2. 逐个上传四包到该 release（multipart，`field=file`）：
   ```powershell
   POST /api/v5/repos/{o}/{r}/releases/{release_id}/attach_files?access_token=$g
   form: access_token, name, file=<octet-stream>
   ```
   返回的 `browser_download_url` 形如 `.../releases/download/v<ver>/<name>`。
3. update.json 里四平台的 `url` 就填这些 Gitee 链接。

---

## 七、更新 update.json + 验证

update.json 四平台键名（必须与 `updater.rs` 的 `current_update_key()` 返回值一致）：

| 平台 | 键名 | 包名后缀 |
|---|---|---|
| Windows x64 | `win-x64` | `.exe` |
| Linux x64 | `linux-x86_64` | 无后缀 |
| macOS Intel | `macos-x86_64` | `.zip`（含 `.app`） |
| macOS Apple Silicon | `macos-aarch64` | `.zip`（含 `.app`） |

每个条目含 `url / size / sha256`（UTF-8 无 BOM）。推 GitHub main。

> ⚠️ **Windows 资产命名一致性**：update.json `win-x64` 的 `url` 中文件名必须与 release 实际上传的资产名完全一致，统一为固定名 `VersePC2.exe`（不带版本后缀）。更新器按 URL 下载并依赖 `size/sha256` 校验，与文件名版本号无关；`build_download_sources` 会从 URL 拆出 `tag` 和 `file` 拼 Gitee/GitHub 镜像，所以**若资产名仍叫 `VersePC2-1.1.x.exe` 而 URL 写 `VersePC2.exe`，镜像链会全部 404**。macOS/Linux 资产名保留平台后缀（如 `VersePC2-macos-x86_64.zip`），与 URL 一致即可。

发布前必验：
- update.json 经镜像拉到的是新版本、四键齐全。
- GitHub 的 `releases/download/v<ver>/...` 直连与 `ghfast` 镜像均 **200**。
- Gitee 四个下载链接 **200 且 Content-Length == size**。
- 若任一链接 404（多为 release 被变草稿/untagged），按第四节「不要 delete+recreate tag」的方式修复后再验。

## 八、常见坑速查

| 问题 | 原因 | 对策 |
|---|---|---|
| `releases/download/<tag>/...` 返回 404 | release 因重删 tag 变成草稿/`untagged` | 用 PATCH force-update tag，不用 delete+recreate |
| macOS/Linux CI 编译失败 | 本地 Windows 只验了 windows cfg 分支 | 本地改 cfg 后必须走 CI 全量验证 |
| 下载到 80% 报错 | 30s 空闲超时把慢连接误判失效 | 已提至 60s；客户端仍用 `Range` 断点续传 |
| 直连 GitHub 下载慢/断 | 网络被墙 | 用 ghfast.top 等镜像 + curl `-C -` |
| update.json 旧客户端读不到新版本 | 没推 main / 顺序问题 | update.json 必须先于或随发布完成推 main |

## 九、一次发布的精简清单

- [ ] 改代码、升版本（Cargo.toml / tauri.conf.json / Info.plist 三处一致）
- [ ] `prepare-frontend` + 本地重编 Windows，落盘并记录 win 哈希/大小
- [ ] 推送所有改动文件到 GitHub main
- [ ] GitHub 建 tag + release（非草稿），上传 Windows 包
- [ ] GitHub Actions dispatch，三 job 全绿
- [ ] 下载/取 digest 得到 mac/linux 包的 size + sha256
- [ ] Gitee 建 release，上传四个包
- [ ] 更新 update.json（四平台 url/size/sha256）并推 main
- [ ] 验证：GitHub 直连 + ghfast + Gitee 四链接均 200 且 size 一致、update.json 经镜像为最新
